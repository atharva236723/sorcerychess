# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sorcery Chess — a two-player chess variant on a 12×12 board with four custom "spellcaster" pieces, wrapped in a small SPA "website" shell (local-only login/signup, navbar, in-app content pages) plus a handful of **standalone MPA pages** for SEO (see "Standalone MPA pages" below). Pure static HTML/CSS/JS with zero dependencies, no build step, no tests, and no framework.

The site was originally one monolithic `index.html`; it has since been split by feature so each section is easy to find and edit. `index.html` is now a thin shell — the `<head>`, the page markup (`<body>`), and an ordered list of `<link>`/`<script src>` tags. **Styles** live in `css/` (linked in cascade order: `base` → `home` → `board` → `components` → `themes` → `responsive`). **Logic** lives in `js/` as plain (non-module) classic scripts that all share one global scope, so **load order is fixed** — `state` first, `boot` last (see the `<script>` block at the end of `index.html` for the canonical order). The split is purely organizational: concatenating the files in tag order reproduces the original single-file behavior byte-for-byte. There is still no build step, no bundler, and no `import`/`export` — it stays zero-dependency and opens straight from `file://`.

The `js/` modules, in load order: `state` (constants + global mutable state), `rules` (piece/move/ability generation, `newGame`), `sound`, `persistence` (save/load), `check` (check/mate, `kill`, `updateGameState`), `turn` (`doMove`/`doAbility`/`doRevive`/`endTurn`/`showEnd`), `clock`, `render` (`onCellClick`, `render`, animations), `ui` (modals, 2D/3D camera, fullscreen, toast, bgfx), `theme`, `ai`, `account` (users/rank/points/stats/champion), `profile`, `hierarchy` (Hall of Ascension + the `showPage` router), `leaderboard` (the Worldwide Leaderboard + clickable player dossier), `showcase` (the two decorative IIFEs), `match`, `variant` (the home "choose your game" dropdown + modes filtering), `points` (the Points & Ranks scoring explainer page), `online` (PeerJS), `fx` (fate waiver, music, dark-summoning), `boot` (`enterSite`, auth wiring, Lenis, `init`). The `css/` files carry the matching slices (`leaderboard`, `variant`, `points` ride between `components` and `themes`). When you need a function, the module names above tell you which file to open.

### Game variants

The site offers two kinds of chess, chosen from a glass dropdown on the home hero (`#variantBtn`/`#variantMenu`, built in `js/variant.js` from the `VARIANTS` table in `state.js`): **sorcery** (the headline 12×12 spellcaster game, the default) and **classic** (pure traditional 8×8 — standard back rank, no spellcasters, reuses the existing move generators). (A third 3-player "triangular" variant was removed and is slated to return later.) Because of variants, **`N` is no longer a `12` constant** — it's a `let` (still in `state.js`) that `newGame()`/`loadGame()` set from the active variant's `size`. The CSS board-fit math is parameterised the same way: `--cols` (default 12 in `base.css`, written each `render()` from `N`) replaces the hardcoded `12` in the `--cell` clamps, the `repeat(--cols,…)` grid, and the `.board-wrap`/`#panel`/`.gravebar` widths — a smaller board just gets larger squares. `VARIANT` is the current/last game's variant (committed in `beginMatch` from `pendingVariant`, restored by `loadGame`, persisted in `sorceryChessSave`); `pendingVariant` is the dropdown choice for the *next* match (persisted separately as `sorceryChessVariant`), kept distinct so changing the dropdown never corrupts a live game's saved board. The modes page filters its battle cards to the variant's `battles` list and swaps in a `#soonNote` for not-yet-playable variants (`updateVariantUI`, called from `showPage('modes')`). Online sync: the host commits its `pendingVariant` and sends `{kind:'hello',variant}`; the joiner waits for that hello (handled at the top of `netHandle`) before running `newGame()`, so both boards match. `render()` also sets the titlebar (`#boardTitle` = variant name, `#boardDim` = `N × N`) and toggles `body.variant-classic`, which hides the spellcaster piece guide. The home hero also carries a **Leaderboard** button (`.cta-alt`, routes via the `.nl` handler) beside "Play now".

The engine still carries light N-player scaffolding from when a 3-player triangular variant existed (`PLAYER_COLORS`/`eliminated` globals, the `GRAVE_ID`/`GCOUNT_ID`/`TIMER_ID` maps, per-color clock/graveyard loops). With triangular removed, `PLAYER_COLORS` is always `['white','black']`, so this is harmless and just makes re-adding the variant later easier. When triangular returns it will need: a `VARIANTS` entry, its own `js/triangular.js` + `css/triangular.css`, the triangle mask/setup/turn-rotation/king-capture-elimination branches back in `rules`/`turn`/`check`/`clock`/`render`/`persistence`, the third `red` army's glyphs + gravebar DOM, and a `VARIANT_MULT.triangular` entry.

## Running

Serve the folder over HTTP (configured in `.claude/launch.json` as the `game` server):

```
python -m http.server 8123
```

Then open `http://localhost:8123/`. Opening `index.html` directly from disk also works. Prefer the `preview_start` tool (server name `game`) over Bash for previewing changes.

## Architecture (split across the `js/` modules; globals shared in one scope)

Global mutable state: `board` (12×12 array of piece objects or null), `turn`, `selected`, `mode` (`'move' | 'ability' | 'revive'`), `graveyard` (one array per active color), `gameOver`, `checkState`, `lastMove` (squares highlighted from the previous action), `clocks` (seconds remaining per active color), `PLAYER_COLORS`/`eliminated` (the turn roster + who's out — currently always white/black; N-player scaffolding left in place for a future triangular variant).

Site shell: the site is **publicly usable without an account** — a first-time visitor (and crawlers / the AdSense reviewer) lands straight on the home content and can browse and play as a **guest**. This is why `index.html`'s `<body>` ships with `class="authed guest"`: `authed` reveals the shell (`#topnav`/`#footer`, the `.page` views) without a login wall, and `guest` swaps the navbar's profile chip / rank / "Log out" for a single "Sign in" button (`#signinBtn`). At boot, `boot.js`'s IIFE calls `enterSite(user)` if a saved session exists, else `enterGuest()` (adds `authed`+`guest`, lands on home, restores any saved match — the account painters `updateRankUI`/`updateStatsUI`/`updateModeLocks`/`updateAvatarUI` all no-op gracefully with no session, and `awardPoints`/`recordResult` early-return, so guest games simply don't save rank/stats). Signing in is **optional** — it only persists rank/stats across sessions. The auth card (`#authView`) is no longer a full-screen wall: it's `display:none` by default and shows either as the pre-JS/signed-out fallback (`body:not(.authed)`) or as a dismissable modal overlay when a guest clicks "Sign in" (`body.show-auth` → fixed overlay; `openAuth()`/`closeAuth()`, closed by the `.authx` ✕ or a backdrop click). `enterSite` clears `guest`+`show-auth`; `performLogout` drops back to `enterGuest()` (never a wall). Users live in localStorage `sorceryChessUsers` ({emailLower:{name,email,hash,points}} — passwords stored as SHA-256 via `hashPass`, never plaintext) and the session as `sorceryChessUser`; `enterSite(user)` adds `body.authed`, lands on `page-home`, and quietly restores any saved match (`gameBooted`). `showPage(name)` switches the `.page` views (home → "Play now" → modes → play, plus the `codex` Spellcasters page, the `leaderboard`, `points` and `profile` pages; the `PAGES` array must list every id, since `showPage` toggles `page-<id>.active` across it — about/contact/privacy are **no longer** in it, they're standalone files now) and keeps `clockPaused` true whenever the player isn't authed *and* on the play view — the 200ms clock interval early-returns on it (so does autosave). The navbar has **no** Play link (it was removed); the home hero's "Play now" CTA (`playNowBtn`) resumes a booted game (`gameBooted && !gameOver → 'play'`) or otherwise opens modes, and the footer "Play now" link routes the same way via the `.nl/.fl` handler. Any element with class `nl`/`fl` and a `data-page` is a router link (the delegated click handler binds **all** of them, not just navbar/footer — e.g. the home hero's "Meet the spellcasters" link and the codex page's CTA), but `showPage`'s active-state styling only toggles `#topnav .nl`. **A `.nl`/`.fl` link with NO `data-page` (and a real `href`) is treated as an external/MPA link — the handler early-returns so the browser navigates normally**; this is how the navbar/footer About/Contact/Privacy/Terms links reach the standalone pages. A match only starts from the modes page (`startMatch`→`beginMatch`; the old `newGameModal` is now the abandon-live-game confirm, honouring `pendingMatch`); the panel's "Exit game" (`requestExitGame`) confirms via `#exitModal` when live progress is at stake, then `exitGame()` cancels any pending `aiTimer`, sets `gameOver`/`gameBooted=false`, clears the save and returns home; the win overlay's "Play again" replays the same mode. Logout keeps the save. The `wipeBtn` (delete account + all `sorceryChess*` keys, removing `sorceryChessUsers` only when no accounts remain) and the contact form now live on the standalone `privacy.html`/`contact.html` pages with their own self-contained inline scripts — **not** wired in `boot.js` anymore. (The contact form `fetch`-POSTs straight to Web3Forms — see "Contact form" below.) The board-fit `--cell` math reserves ~55px for the navbar (270px constant).

Standalone MPA pages: for SEO, the legal/company/error pages are **real crawlable HTML files** served at their own URLs, not SPA views behind the login gate — `about.html`, `contact.html`, `privacy.html`, `terms.html` (the last is new), plus error pages `404.html`/`500.html`. Each carries its own per-page SEO `<head>` (title/description/canonical/OG/Twitter + `BreadcrumbList`/page-type JSON-LD; error pages are `noindex`), an always-visible `.site-nav` + `.site-foot` (the standalone twins of the auth-gated `#topnav`/`#footer`), and a small inline script that applies the saved `sorceryChessTheme` so they match the user's skin. They share `css/base.css` (design tokens, `.pagebox`, inputs) + `css/themes.css`, and a dedicated `css/pages.css` (ambient backdrop copy, the standalone nav/footer, error layout). They are surfaced on the home view by the `.explore` band (styled in `home.css`) and linked from the navbar/footer; `sitemap.xml` lists the indexable ones. For server config, point your 404/500 handlers at these files (on a static host like nginx: `error_page 404 /404.html;`). To add another standalone page, copy an existing one and keep `css/pages.css` for the chrome.

Contact form (Web3Forms, no backend): the site is **100% static** — there is no Worker. `contact.html`'s inline script POSTs the message directly to **Web3Forms** (`https://api.web3forms.com/submit`) as JSON, so the destination email never appears in any served file. The only token in the page is a **public access key** (`ACCESS_KEY` near the top of that script) — Web3Forms designs it to be exposed; it just routes submissions to the owner's inbox. The script validates/trims fields client-side, drops honeypot (`company`) submissions with a fake success, and only attaches `email`/`replyto` when the visitor gave an address. It degrades gracefully (shows an error) if the request fails — e.g. offline, or before a real `ACCESS_KEY` is filled in. Deployment is a plain static-asset deploy: `wrangler.jsonc` has **no `main`/Worker and no secrets**, just the `assets` block (`wrangler deploy` uploads the files; live at `sorcery-chess.<account>.workers.dev`, custom domain added via a route once `sorcerychess.com` is owned). A `_headers` file adds site-wide security headers (nosniff, frame-options, referrer-policy, permissions-policy, HSTS) and forces HTML to revalidate (so a stale `index.html` can't pair with newer `js/*`). (History: the form previously used `mailto:`, then a Cloudflare Worker relaying through Resend; both were dropped in favour of Web3Forms to keep the site dependency-free and backend-free.)

Spellcasters codex (`#page-codex`, "The Grimoire", reachable from the navbar "Spellcasters" link, a footer link, and the home hero's "Meet the four spellcasters" link): a showcase page for the four custom pieces. Each `.spell` glass card pairs a hand-built SVG **sigil portrait** (`.sigil` — a glyph medallion with two counter-rotating dashed rune rings via `@keyframes sigspin`, themed only in `--ink`/`--magic`, no raster assets) with lore, a numbered how-it-works list, stat chips, and a looping **mini-board spell demo** that visually performs the piece's mechanic (the project's dependency-free stand-in for a "video" — no image/video files anywhere). The demo engine is one IIFE keyed off `#page-codex`: `SPECS` declares each spell as `{pieces, acts, hold}` where `acts` are timed steps (`at` = ms after the previous step) calling a small action set on a 5×5 board — `move`/`swap`/`tag`/`untag`/`cast`/`beam`/`kill`/`revive`/`say`. `Demo(host,spec)` builds the grid + pieces and loops the script (skipping the loop under `prefers-reduced-motion`); `window.__codexDemos.{start,stop}` is driven by `showPage` (start only when `name==='codex'`) and a `visibilitychange` listener, mirroring the homepage showcase. Demo pieces keep their square via a `transform:translate` on `.demo-pc` while death/revive/scale animate the inner `.pc-glyph` (same split-layer reason as the real board's `.piece`/`.pbody`). The demo board uses soft #f3f3f3/#141414 squares (a UI element, not the real strict-B&W game board).

Theming: a navbar `#themeBtn` opens a glass dropdown (`#themeMenu`, swatches built in JS from the `THEMES` array) of **six site-wide colour skins** — `dark` (Obsidian, the default), `light` (Daylight), `crimson`, `sapphire`, `emerald`, `amethyst`. `applyTheme()` clears every `theme-*` class then, for any non-default theme, adds `theme-<id>` to *both* `<html>` (drives the page-background gradient via `html.theme-X`) and `<body>` (swaps the glass + accent CSS-var set via `body.theme-X`); the choice persists as `sorceryChessTheme` (theme id; legacy `'light'`/`'dark'` saves still map through). The look is glassmorphism: surfaces use the shared `--glass`/`--glass-strong` translucent gradients + `backdrop-filter:blur(var(--blur))` and a per-theme `--accent`/`--accent-rgb` that flows through chrome (glows, links, progress fills, hovers). `--magic` (board spellcaster blue) is deliberately **not** themed, and the board itself stays strict black & white in every skin. Overlays (the hierarchy hall `#hierModal .hall` and every `.modal .box`) keep their own dark `--over*` palette regardless of theme, so their light content stays readable — this is what fixed light-mode rank names vanishing in the Hall of Ascension. The hall's scroll container `#hallScroll` carries `data-lenis-prevent` so the mouse wheel scrolls the hall rather than the Lenis-driven page behind it. Coloured themes also `hue-rotate` `#bgfx` so the ambient orbs/runes match (crimson/emerald). The play panel carries a `#modeBanner` (set in `render()`) that names the current opponent — "Facing <AI name> · Level N" for `gameMode==='ai'`, "Local Match" otherwise; against the two dread AIs (`aiLevel>=4`) it gets the `.dread` red treatment and `render()` also adds `body.horror`, whose `#page-play.active::before` fixed overlay drenches the whole play view in a pulsing red vignette.

Rating ladder: 17 ranks (`RANKS`, Junior → The Monarch) climbed with points stored per-account (`points` on the user record, missing = 0). `showEnd` pays the gain — base `WIN_POINTS` 10/25/50/120/200 for beating AI levels 1–5 (white wins only), `FRIEND_POINTS` 10 for local matches, nothing for draws/losses — via `awardPoints`, which returns old/new rank indices so the overlay's `#rankLine` can announce "+N points" and rank-ups. **Points are scaled per variant**: `VARIANT_MULT` (classic ×1, sorcery ×1.5) multiplies every award *and* the loss penalty, so the canonical figures are read through `winPoints(level,v)` / `friendPoints(v)` / `lossPenalty(v)` (all default to the active `VARIANT`) — `showEnd` and `pointsAtRisk` call these, never the raw `WIN_POINTS`/`FRIEND_POINTS`/`LOSS_PENALTY` constants. `updateRankUI()` (called from `enterSite` and `awardPoints`) refreshes the navbar chip `#whoRank` and the home hero's `.rankcard` (rank, tier x/17, progress bar to the next threshold).

Per-variant defeats: which AI difficulties an account has beaten is tracked **separately per chess type** — beating the Apprentice in Sorcery does not unlock the dread foes in Classic. It lives on the user record as `beatenV` ({sorcery:[levels], classic:[…]}); a legacy flat `beaten` array predates variants and is read as (and folded into, on first `markBeaten`) the sorcery bucket via `beatenFor(u,variant)`. `markBeaten` writes the just-won `VARIANT`'s bucket; `beatenLevels(variant)`/`isUnlocked(level,variant)`/`updateModeLocks()` all default to `pendingVariant` (the dropdown's choice the modes page is showing), and `setPendingVariant` re-runs `updateModeLocks()` so switching variants re-shows that variant's lock/✓ state.

Worldwide Leaderboard (`#page-leaderboard`, `js/leaderboard.js` + `css/leaderboard.css`): ranks the top 20 of one chess type at a time — a fixed roster of `LEGENDS` (NPC mages, each with a `title` epithet + `lore` line; non-sorcery variants reshuffle their renown via a deterministic per-legend factor in `legendVStats`) plus every local account (per-variant renown from `u.vstats`). `lbVariant` follows `pendingVariant` on open but switches live via the `#lbVariants` tabs; `renderLeaderboard` builds a top-3 podium + a 4–20 list and stores the ranked field in `lbField`. **Every contender is clickable** (podium card, list row, or the below-20 "your standing" row — all carry `data-pos` + are keyboard-activatable): delegated click/Enter handlers on `#lbPodium`/`#lbList`/`#lbYou` look the player up in `lbField` and call `openPlayerCard(p)`, which fills the `#playerModal .pcard` dossier — an aura-tinted hero (the player's `auraRgb`, or a name-hashed `lbAuraRgb` for legends), the `rankEmblem(rankOf(points))` crest as a watermark, avatar/medal, name + epithet, rank/realm/favoured-caster chips, two headline numbers (global #pos, renown), a progress bar to the next rank, a 2-col stat grid (win rate/wins/losses/battles, plus best-streak + "sorcerer since" for real accounts), and a lore/bio blockquote. The card is `display:block` (a flex column would shrink the hero on tall cards and clip its `overflow:hidden` chips); its `--pa` CSS var carries the aura rgb that tints the whole card. Closing rides the generic `.modal` click-outside handler plus its own `#pcClose` ✕.

Scoring page (`#page-points`, "Points & Ranks", `js/points.js` + `css/points.css`, reachable from the navbar "Scoring" link, a footer link, and the modes-page subtitle): a glass explainer for the rating system. `renderPoints()` (called by `showPage('points')`) builds three per-variant **stakes cards** (`ptsVariantCard` — multiplier badge + win-by-difficulty table + friend/loss lines, all via the `winPoints`/`friendPoints`/`lossPenalty` helpers so the page can't drift from what the game pays), a live **"your standing"** panel from the signed-in account (`ptsYouHtml` — current rank, what a win/loss is worth right now in `pendingVariant`, foes cleared n/5, progress bar), and the **17-rung ladder** (`ptsLadderHtml`, Monarch at top, the player's rung lit). Static prose covers per-variant defeats, the dread-foe unlock chain, the above-the-Arcanum loss rule, and what never scores.

Career stats: alongside `points`, each user record persists a lifetime record — `games`, `wins`, `losses`, `draws`, `streak` (current win streak), `bestStreak`, `joined` (signup timestamp, ms) and `lastPlayed`. `showEnd` calls `recordResult(winner)` once per game (the player is always White, so `winner==='white'` is a win, `'black'` a loss, null a draw; a draw or loss resets the streak). Fields are read with `||0`/`||` fallbacks so pre-stats accounts upgrade silently (`joined` is backfilled on first result). The home `.rankcard` carries a `#statGrid` (Battles / Victories / Win rate / Best streak) plus a `#memberLine` ("Sorcerer since <Mon Year>"); `updateStatsUI(animate)` paints them — `animate=true` runs `animateCount` easeOutCubic count-ups, fired each time `showPage('home')` opens the home view (`enterSite` paints once without animating). A best streak ≥3 gets the blue `.glow` magic treatment on the Best-streak cell.

Computer opponent (`gameMode==='ai'`, black; `aiLevel` 1–5 = Apprentice/Sorcerer/Archmage/The Malevolent/The Dominion, both persisted in the save): `scheduleAI()` is called at the end of every `endTurn` (and on save-restore) and fires `aiMove()` after `AI_DELAY`; the AI executes through the same `doMove`/`doAbility` entry points as a human, so animation/sfx/check rules/persistence come free. `aiActions()` collects `movesFor`+`targetsFor` (check-escape filtering included); scoring is material via `aiEval` where `aiWorth` discounts poisoned (×.2) and frozen (×.85) pieces — that one function prices abilities (poison/freeze/cure) and ordinary captures on the same scale (`aiEval(true)` adds positional terms: pawn advance, centralisation, king-to-rim; at levels 4–5 it also adds king-hunt aggression — black pieces paid by Chebyshev closeness to the white king, white attackers penalised near the black king, white king pushed rimward). The ladder is a deliberate staircase: level 1 is random-but-king-safe (70% of the time it takes the most valuable capture on offer), level 2 greedy 1-ply with ±10 noise (`aiScore` = eval minus white's best snap-back, `aiBestCapture`). Levels 3–5 run `aiPickDeep` → `aiAB`, a real alpha-beta (captures-first ordering via `aiMovesAll`, branches hitting a king return ±(900000+depth) so faster kills win the tie-break, every-256-node `performance.now()` deadline check) at depth 2/1.5s, 3/2.5s and 4/4.5s respectively; `aiPickDeep`'s root ranking uses the positional eval and bumps checking moves (+45) so the budget goes to forcing lines — the think runs synchronously inside `aiMove`, paid from black's own clock; choosing level 4 or 5 shows the sarcastic `#fateModal` waiver (`FATE_MSGS`, accept → `startMatch`, reject → toast). King-hangs price out through `AI_VAL.king`. Sims mutate and restore `board` directly (`aiApply`/`aiUndo`), like `hasEscape`. The AI never uses the Witch's revive. `onCellClick` ignores input while the computer is moving; `render()` shows "Your move"/"<name> is thinking…" and `showEnd` rewrites wins to You/<AI name>.

`.board-wrap` width is pinned to `calc(var(--cell)*12 + 6px)` and the titlebar status is nowrap/ellipsis — the wrap's width must never depend on text, because a wider wrap moves the `perspective-origin` and visibly re-projects the tilted slab (this was a real bug: the status flipping to "… is thinking…" shoved the board sideways every move).

In-progress games persist to localStorage (`sorceryChessSave`, written each `endTurn`, cleared by `showEnd()`/`newGame()`; restored by `loadGame()` when a session resumes). Sounds are synthesized in `sfx(kind)` with WebAudio — no audio assets; the mute flag persists as `sorceryChessMuted`. Every player action must set `lastMove` and call an appropriate `sfx`.

A piece is a plain object from `makePiece(type, color)`: `{type, color, poison, frozen, moved}` plus `charges` (wizard) or `cd` (freezer cooldown). Captured pieces move to `graveyard[color]` — they are never destroyed, because the Witch can revive them.

Key flow: every player action (`doMove`, `doAbility`, `doRevive`) ends by calling `endTurn()`, which ticks down poison/freeze/cooldown counters for the mover's pieces (poison reaching 0 kills), switches `turn`, calls `updateGameState()` (check/checkmate/stalemate detection), and calls `render()`.

Online play (`gameMode==='online'`, PeerJS WebRTC, loaded from the same CDN as Lenis): a third opponent type alongside `'friend'`/`'ai'`. The "Play online" modecard opens `#onlineModal` (host **creates** a room → short `genCode()` code used as the PeerJS id `PEER_PREFIX+code`, or **joins** one). When the data channel opens both sides run `beginOnline(host)` — host is White, joiner Black (`myColor`) — then the deterministic `newGame()`, so boards start identical. Every local action calls `netSend()` from inside `doMove`/`doAbility`/`doRevive` (guarded by `!applyingRemote`); the peer's `netHandle()` replays it through those *same* entry points with `applyingRemote=true` so it doesn't echo. `onCellClick` ignores input while `turn!==myColor`. `RTC_CONFIG` adds public Google STUN + free OpenRelay TURN so connections survive strict NATs. Online duels are deliberately **clockless** (`useTimer=false`, sidesteps clock-sync drift) and **unranked** (`showEnd`'s online branch skips `recordResult`/`awardPoints` and phrases the result You/Opponent); the win overlay's "Play again" routes through `rematch()` (sends `{kind:'rematch'}` so both reset). `onPeerLost` ends a live match as a win for whoever stayed. `saveGame()` early-returns for online (a P2P session can't be restored), and `exitGame()` calls `netTeardown()`.

Fullscreen play (`#fsBtn` in the panel, plus a floating `#fsExit`): `toggleFullscreen()` requests the native Fullscreen API on **`document.documentElement`** (not `#page-play` — so the body-level win overlay and confirm modals still render over the board) and a `fullscreenchange` listener mirrors the state into `body.fsplay`; if the API is blocked it falls back to the class alone (`setFsClass` just toggles the class — all the motion is pure CSS). The transition is a smooth crossfade: `--cell` is defined on `body` as `calc(var(--cellnormal)*(1 - var(--fs)) + var(--cellfs)*var(--fs))`, where `--fs` is a `@property`-registered `<number>` (0→1) with a `.62s` transition — so the whole board and every piece (sized off `--cell`) grow as one. `--fs` must live on the *same* element as `--cell` (body) because the unregistered `--cell` re-substitutes per frame as the registered `--fs` animates; `--cellnormal`/`--cellfs` carry the normal vs fullscreen clamps (the `max-width:700px`/`900px` media queries override `--cellnormal`/`--cellfs` respectively). While the board swells, the surroundings fade out so focus lands on the board + the panel beside it: a fixed `#fsbackdrop` dark stage fades its opacity 0→1 and the ambient `#bgfx` fades to `.12`, all on the same `.62s` curve (`#page-play.active`'s padding eases too). `prefers-reduced-motion` zeroes these transitions for an instant switch. The navbar stays hidden via the existing `body.playing` rule. (The old arcane-burst FX — `#fsfx` rings/runes + `fsBurst()` — was removed in favour of this crossfade.)

The Hall of Ascension (`#hallScroll`) scrolls with its **own** Lenis instance (`hallLenis`, created lazily by `ensureHallLenis()` with `{wrapper, content}`), driven from the same single rAF loop as the page `lenis`, so its inertia matches the rest of the site instead of native snapping. `openHierarchy()` uses `hallLenis.scrollTo` for both the reset-to-top and the "descend to where you stand" glide; it still carries `data-lenis-prevent` so the page Lenis ignores it.

Every *other* inner scroll surface is smoothed the same way through a generic helper: `attachLenis(el, opts)` creates a Lenis bound to that element (`{wrapper: el, content: el}` — fine for a plain overflow box), pushes it onto the `subLenis[]` registry that the single rAF loop also ticks, sets `data-lenis-prevent` (so the page Lenis doesn't double-consume those wheels), and attaches a `ResizeObserver` that calls `inst.resize()` — this is what lets a box that boots at `display:none` (every modal) measure correctly the moment it's shown or its content grows. All instances share one easing (`LENIS_EASE`). At boot `initScroll()` attaches it to the game side `#panel` and every `.modal .box`, so the whole site (page, hall, panel, modals) glides with identical inertia. Add a new scroll container by calling `attachLenis(el)` once after it exists — don't spin up a private rAF loop.

The board is 3D but not manually rotatable: `#board` transforms with `rotateX(var(--tilt))` under a perspective on `.board-wrap`. The 2D/3D mode button animates the camera via `tweenView()` (rAF easing of `--tilt`; 2D = tilt 0); the mode persists as `sorceryChessView`, and `#board`'s negative `margin-top` compensation scales with `cos(var(--tilt))` so the flat view doesn't overlap the graveyard bar. The piece guide is hidden by default (`sorceryChessGuide` remembers the user's choice). Every `newGame()` plays an intro: `introPending` makes the *next* render (only) add `#board.intro` — the slab drops in (`boardIn`), cells fade center-out via inline `animation-delay`s, edges/shadow fade — then the opening cascade spawns pieces with `INTRO_MS`-offset center-out `delay`s consumed by `applyAnims` (`backwards` fill keeps pieces hidden until their turn). Four `.edge` divs (slab side faces) are re-appended after the 144 cells on every render — cell lookups rely on `boardEl.children[r*N+c]`, so cells must stay first.

Each piece is two layers: `.piece`, a flat anchor in the board plane (slide animations translate the *anchor*), and `.pbody`, the visible glyph disc (carries colors, magic aura, poison/freeze tags), lifted by `translateZ` and counter-rotated with `rotateX(-tilt)` — the lift must come *before* the counter-rotation — so it always stands upright facing the camera. Never put `opacity`/`filter` on `.piece` itself — it flattens the 3D child (that's why `.frozen` fades `.pbody` instead). `.ghostfly` ghosts are plain 2D discs with their own styles. Performance matters here: a previous many-elements-per-piece design caused visible lag, so keep pieces to one visible element and avoid `filter:blur`/`drop-shadow` in the 3D scene; `applyView()` batches view-var writes to one per frame.

`render()` rebuilds the entire board DOM from scratch on every change. Animations work via two queues consumed at render time:
- `pendingAnims` — pieces sliding between squares (CSS transform from the old offset back to 0).
- `pendingFlights` — "ghost" copies flying between the board and the graveyard bars (fixed-position elements animated across the viewport).
Any board mutation that should animate must push to these queues *before* `render()` runs.

### Game rules that differ from standard chess

- Win by capturing the King (`kill()` triggers `win()`), or by checkmate (`updateGameState()`). Moving into check is legal *except while already in check* — and except for the King himself: `movesFor` always filters the King's own moves to safe squares (so a king can still die to a discovered attack, but never walks into one). `movesFor`/`targetsFor` (the only move/target sources `render()` and `onCellClick()` may use — never raw `legalMoves`/`abilityTargets` there) filter to check-escaping actions when `checkState==='check'`, and the Witch's revive is disabled during check. Game ends call `showEnd(text, winner)`; a non-null winner adds `#overlay.won` and `celebrate(color)` fills `#celebr` with looping glyph-firework spans (cleared in `newGame()`).
- Spellcasters: all four are **queen-movers** (slide along all 8 lines). Wizard (poisons an enemy and swaps places; 4 charges, and `WIZARD_COOLDOWN` makes him recharge for 2 own moves between casts — a ✶ tag shows the count and a `toast()` notice fires when ready), Alchemist (cures a poisoned ally and swaps), Freezer (queen-mover that never captures; freezes an enemy for `FREEZE_DURATION` (3) moves and swaps, then cooldown), Witch (revives a graveyard piece onto her own square and dies in its place).
- Abilities target only the *first* piece along the user's own movement lines (`abilityTargets`) — i.e. all 8 directions for every spellcaster, matching their queen movement. Wizard/Alchemist/Freezer targets glow blue and are clicked directly on the board (`DIRECT_ABILITY`); the Witch uses the panel button + graveyard tokens.
- Check detection (`inCheck`) treats "any enemy pseudo-legal capture of the king" as check; frozen pieces give no check. Checkmate/stalemate search (`hasEscape`) simulates moves *and* abilities by mutating `board` and restoring it — e.g. freezing the checking piece counts as an escape. A Witch revive never changes attacked squares, so it counts for stalemate avoidance but never as a check escape.
- No castling or en passant. Pawns promote to Queen only.
- Chess clock: each side starts with `clockStartFor()` seconds — `CLOCK_START` (300s) normally, but `DREAD_CLOCK` (180s / 3 min) against the Malevolent or the Dominion (`gameMode==='ai' && aiLevel>=4`). Every action grants `CLOCK_INCREMENT` (+2s) in `endTurn`. A 200ms interval ticks the mover's clock, autosaves every ~2s, and flag fall ends the game ("X wins on time"). Clocks persist in the save (and `loadGame` falls back to `clockStartFor()` after restoring `gameMode`/`aiLevel`).

## Conventions

- Keep everything dependency-free and build-step-free: plain HTML/CSS/JS, no bundler, no `import`/`export`, must still open from `file://`. (`poster.html` / `poster-social.html` remain standalone single files.)
- **One feature, one file.** When you add a feature, put it in a **new `js/` file** (and a new `css/` file if it needs meaningful styling) rather than swelling an existing one, then wire it with an ordered tag in `index.html`: a `<link>` in the right cascade slot, and a `<script src>` **before `js/boot.js`** (boot runs `init()` last and assumes everything else is already defined). Because every script shares one global scope, just define your functions/globals top-level and they're callable from the others. Touch the smallest file that owns the section instead of scrolling one giant file.
- Visual language: strict black & white board/pieces, `--magic` blue (#3da9ff) reserved for spellcaster abilities, red only for check warnings. Inter font, dark UI panels.
